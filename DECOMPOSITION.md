## Feature: User Notification Preferences

The goal is to let users choose how they receive notifications. The available options are `email`, `sms`, and `none`, with `none` as the default.

The feature will follow the existing routes → services → repositories structure. Each subagent will work in a fresh Claude Code session.

## Divergence

**Did Claude follow each subagent's constraints?**

Yes. All four subagents reported following their assigned file boundaries: SA-1 modified only `repositories/users.py`, SA-2 only `services/users.py`, SA-3 created only `routes/users.py`, and SA-4 changed only `tests/test_users.py` and `tests/test_user_routes.py`. No constraint violations were reported.

**Did any subagent's output break the next subagent's assumptions? How did you recover?**

- **Field name (SA-1).** SA-1 stored the field as `notification_preference`, but the assignment requires `notification_pref`. This was caught before SA-3 and fixed in a follow-up session that renamed the key in `repositories/users.py` only. Function names and signatures stayed the same, and `services/users.py` did not reference the key directly, so nothing else needed to change. After the rename, pytest showed 61 passed and Ruff passed.
- **Missing user list function (found by SA-4).** The assignment requires user list responses to include `notification_pref`, but no user list function exists in any layer. Only the detail function, `get_user`, exists. SA-4 tested that `get_user` includes `notification_pref` and that every stored user record has the field, but it could not test a list response because there is none. Because production files were outside SA-4's scope, SA-4 reported the gap instead of fixing it. **Resolved in the user-list follow-up:** in a separate session approved after SA-4, `get_all_users()` (repository), `get_users()` (service), and `list_users()` (route) were added along with 11 tests. Every listed user now includes `notification_pref`. Pytest went from 88 to 99 passed, and Ruff passed.
- **Mutable stored dictionaries (found by SA-4).** `get_user` and `update_notification_preference` return the dictionary stored in the repository, not a copy. Any caller that edits a returned user changes the stored record directly, which skips the service-layer validation (for example, setting `notification_pref` to `"push"`). This did not cause any test failures. **It is still an unresolved design risk.** The new `get_users()` returns copies, and a test checks that, so the list response is safe. But the follow-up was told not to change `get_user` or `update_notification_preference`, so they still return the stored dictionaries.

**Would I change the decomposition if I did this again?**

Yes. The decomposition only covered reading and updating the preference, so no subagent was assigned the user list requirement. The gap only showed up at the end, in SA-4, when nobody with production scope was left to fix it, so it took an extra follow-up session to resolve. Next time I would either add the user list function to SA-1 through SA-3, or add a production verification step before SA-4 that compares the code against every requirement in the assignment (including the field name and the list and detail responses). That check would also have caught the `notification_preference` naming mistake without needing a separate follow-up session. I would also have SA-1 decide whether repository functions return copies, so later layers don't inherit the mutable-dictionary problem.
